## Principles

1. The database enforces invariants; application code is the second line of defense.
2. Schema is created by **versioned migrations**, not `spring.jpa.hibernate.ddl-auto=update` (which is fine for throwaway experiments only).
3. Every foreign key and every frequent filter/sort has a deliberate index decision.
4. Money = integer minor units; time = `timestamptz` UTC; IDs = UUID generated by the application (no round-trip to read back generated keys; but random UUID primary keys fragment B-tree indexes — consider time-ordered UUIDv7 if insert rate is high).

## Schema (Phase 2)

```sql
-- [ILLUSTRATIVE] PostgreSQL-flavoured
CREATE TABLE orders (
    id              UUID PRIMARY KEY,
    customer_id     UUID        NOT NULL,
    status          VARCHAR(20) NOT NULL
                    CHECK (status IN ('CREATED','CONFIRMED','REJECTED','CANCELLED','SHIPPED','DELIVERED')),
    total_minor     BIGINT      NOT NULL CHECK (total_minor >= 0),
    currency        CHAR(3)     NOT NULL,
    version         BIGINT      NOT NULL DEFAULT 0,        -- optimistic locking
    created_at      TIMESTAMPTZ NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL
);

CREATE TABLE order_items (
    id                 UUID PRIMARY KEY,
    order_id           UUID   NOT NULL REFERENCES orders(id),
    product_id         UUID   NOT NULL,
    quantity           INT    NOT NULL CHECK (quantity > 0),
    unit_price_minor   BIGINT NOT NULL CHECK (unit_price_minor > 0)
);

CREATE TABLE idempotency_keys (
    customer_id     UUID         NOT NULL,
    idem_key        VARCHAR(64)  NOT NULL,
    request_hash    CHAR(64)     NOT NULL,       -- SHA-256 of canonical payload
    order_id        UUID         NOT NULL REFERENCES orders(id),
    created_at      TIMESTAMPTZ  NOT NULL,
    PRIMARY KEY (customer_id, idem_key)
);
```

Design choices:
- `version` is incremented by Hibernate on each update when the field is annotated `@Version`; the generated update is `UPDATE orders SET ..., version=? WHERE id=? AND version=?` — zero rows updated ⇒ conflict exception.
- `status` stored as a string (readable, order-insensitive). `@Enumerated(EnumType.STRING)`; **never `ORDINAL`** (reordering the enum silently corrupts data).
- `idempotency_keys` shares the transaction with the order insert. The primary key *is* the dedupe mechanism.

## Constraints as invariants

| Invariant | Enforced by | Also enforced by |
|---|---|---|
| One order per `(customer, idempotency key)` | `PRIMARY KEY (customer_id, idem_key)` | Application pre-check (optimisation only, not correctness) |
| Quantity positive, price positive | `CHECK` | Bean Validation / domain |
| Item belongs to an existing order | FK | JPA mapping |
| Status in known set | `CHECK` | Enum |
| No two concurrent updates silently overwrite | `version` column | `@Version` |
| Legal state transitions | **Application (domain)** — hard in plain SQL | Optionally a conditional update `UPDATE … WHERE status = 'CREATED'` |

Conditional update as a lock-free guard **[ILLUSTRATIVE]**:
```sql
UPDATE orders SET status = 'CANCELLED', version = version + 1, updated_at = now()
WHERE id = :id AND status IN ('CREATED','CONFIRMED');   -- 0 rows => illegal/lost race
```

## Indexes

| Index | Serves | Rationale |
|---|---|---|
| PK `orders(id)` | `GET /orders/{id}` | Automatic |
| `orders(customer_id, created_at DESC, id DESC)` | list orders by customer, newest first, keyset pagination | One index satisfies filter + sort; supports keyset `(created_at,id) < (?,?)` |
| `order_items(order_id)` | fetch items for an order; FK joins | PostgreSQL does **not** auto-index FK columns. Without it, FK checks and joins scan. |
| `orders(status, updated_at)` partial/`WHERE status IN (non-terminal)` | reconciler: stuck orders | Partial index keeps it tiny since most orders are terminal |
| PK on `idempotency_keys` | dedupe | Automatic |

Costs: every index slows writes and uses space; add indexes for a measured/known query, and confirm with `EXPLAIN` that the planner uses them. Column order in composite indexes matters (equality columns first, then range/sort).

## Transaction behaviour and locking

- **Default isolation:** PostgreSQL `READ COMMITTED`; MySQL/InnoDB `REPEATABLE READ`; H2 default `READ COMMITTED` **[UNVERIFIED for H2 version in use]**. Know your engine's semantic differences ([handbook](../learning/database-fundamentals.md#isolation-levels-and-anomalies)).
- **Create order:** insert idempotency row first. A concurrent duplicate blocks on the unique index until the first commits, then fails with a unique violation → treat as "already created", load and return the original. No explicit lock needed.
- **Cancel vs confirm race:** both read version *v*; both try `UPDATE … WHERE version = v`; one affects 1 row, the other 0 ⇒ optimistic failure ⇒ reload and re-evaluate (cancel after confirm is still legal; confirm after cancel is not).
- **Hot counters (inventory):** use a single atomic conditional `UPDATE … SET available = available - :q WHERE sku = :s AND available >= :q`. No read-modify-write in Java.
- **Deadlocks:** arise when transactions lock multiple rows in different orders (e.g. reserving items A,B vs B,A). Mitigation: acquire in a canonical order (sort by product ID), keep transactions short, retry on deadlock victim errors. Exercise: [FS-06](../debugging/failure-scenarios.md).
- **Locks and long transactions:** a transaction held open across a remote call keeps row locks and a pool connection ([FS-04](../debugging/failure-scenarios.md)).

## Outbox and inbox tables (Phases 4–5)

```sql
-- [ILLUSTRATIVE] [PLANNED]
CREATE TABLE outbox_events (
    id             UUID PRIMARY KEY,               -- eventId, also the consumer dedupe key
    aggregate_id   UUID        NOT NULL,           -- Kafka key
    aggregate_ver  BIGINT      NOT NULL,
    event_type     VARCHAR(100) NOT NULL,
    payload        JSONB       NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL,
    published_at   TIMESTAMPTZ NULL                -- NULL = pending
);
CREATE INDEX outbox_pending_idx ON outbox_events (created_at) WHERE published_at IS NULL;

CREATE TABLE processed_events (                    -- inbox / dedupe, per consumer
    consumer      VARCHAR(100) NOT NULL,
    event_id      UUID         NOT NULL,
    processed_at  TIMESTAMPTZ  NOT NULL,
    PRIMARY KEY (consumer, event_id)
);
```

- Relay query uses `FOR UPDATE SKIP LOCKED` so multiple relay instances do not collide (PostgreSQL/MySQL 8+; H2 support differs).
- Retention: delete published rows older than N days; delete old `processed_events` beyond the max redelivery horizon.
- Explanation, crash analysis: [distributed systems handbook](../learning/distributed-systems.md#transactional-outbox-and-the-dual-write-problem).

## Migrations

- Tool choice (Flyway vs Liquibase) — **OPEN**, needs an ADR in Phase 2.
- Rules: immutable once applied; one change per file; forward-only; backward-compatible for rolling deploys (expand → migrate → contract); never drop/rename a column in the same release that stops using it.
- Hibernate `ddl-auto`: `validate` (or `none`) once migrations exist.

## H2 vs PostgreSQL fidelity

H2 in-memory is convenient but differs: locking granularity and behaviours, isolation implementation (MVCC mode details), SQL functions, JSON types, partial indexes (not supported the same way), `SKIP LOCKED` support, and error codes. Use H2 for fast feedback on mapping and basic constraints; **do not claim concurrency or performance conclusions** from H2 alone. When a real PostgreSQL is available (ADR-0009), re-run concurrency tests there.
